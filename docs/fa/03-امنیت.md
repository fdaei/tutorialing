# امنیت

هر ریسکی که پیدا شد: چه بود، چطور می‌شد از آن سوءاستفاده کرد، اثر واقعی‌اش چه بود، چطور برطرف
شد، و چطور جلوی برگشتنش گرفته شده.

---

## ۱. ورود به سیستم

اینجا رمز عبور وجود ندارد. ورود فقط با **شماره موبایل و کد یک‌بارمصرف** است.

**چرا بدون رمز؟** رمز عبور یعنی: ذخیرهٔ امن، بازیابی رمز، رمزهای تکراری بین سایت‌ها، و نشت.
حذف کامل رمز، همهٔ این دسته از مشکلات را حذف می‌کند.

### محافظت‌های موجود (بررسی و تأیید شد)

| کنترل | نحوهٔ پیاده‌سازی |
| --- | --- |
| تصادفی‌بودن کد | با `crypto.randomInt` — مولد تصادفی رمزنگاری‌شده، نه `Math.random` |
| ذخیرهٔ کد | HMAC-SHA256 با یک «فلفل» سرور، نه متن ساده |
| انقضا | ۲ دقیقه |
| فاصلهٔ ارسال مجدد | ۶۰ ثانیه |
| سقف هر شماره | ۵ بار در ساعت |
| سقف هر IP | ۱۰ بار در ۱۰ دقیقه |
| افشای وجود کاربر | ندارد — پاسخ برای شمارهٔ ثبت‌شده و ثبت‌نشده یکسان است |

**چرا کد ۶ رقمی را هم HMAC می‌کنیم؟** چون فقط ۹۰۰٬۰۰۰ حالت دارد. اگر با هش ساده ذخیره می‌شد،
کسی که به پایگاه داده دسترسی پیدا کند می‌تواند در چند ثانیه همهٔ حالت‌ها را از قبل حساب کند و
کد را پیدا کند. «فلفل» سرور این حمله را بی‌اثر می‌کند.

**چرا توکن نوسازی (refresh) با هش ساده ذخیره می‌شود؟** چون آن یک عدد تصادفی ۳۲ بایتی است؛
تعداد حالت‌هایش آن‌قدر زیاد است که از پیش محاسبه ممکن نیست. این یک تصمیم آگاهانه است، نه غفلت.

### هزینهٔ واقعی محدودیت نرخ

پیامک پول واقعی خرج می‌کند. بدون سقف، کسی می‌توانست با یک اسکریپت ساده هزینهٔ پیامک شما را
بالا ببرد.

> **این محدودیت آن‌قدر مؤثر بود که وسط همین ممیزی، خودِ من را چند دقیقه بلاک کرد.** نتیجهٔ درستی
> است.

## ۲. توکن‌ها و ابطال دسترسی

توکن دسترسی **بدون حالت** است (JWT) و ۱۵ دقیقه اعتبار دارد. یعنی نقش‌ها و مجوزها را از لحظهٔ
صدور با خودش حمل می‌کند.

**مشکل ذاتی:** اگر کاربری را همین حالا مسدود کنید، توکن قبلی‌اش تا ۱۵ دقیقه هنوز کار می‌کند.

**راه‌حل:** یک «نشانگر ابطال» در Redis. هر بار که کاربری مسدود می‌شود یا نقشش تغییر می‌کند،
زمان آن لحظه ثبت می‌شود و هر توکنی که **قبل** از آن صادر شده رد می‌شود.

> ⚠️ **نکتهٔ مهم برای توسعه‌دهندگان:** هر کدی که کاربری را مسدود می‌کند یا نقش/مجوزش را عوض
> می‌کند، **باید** `TokenRevocationService.revokeUser()` را صدا بزند. بدون آن، دسترسی قدیمی تا
> ۱۵ دقیقه باز می‌ماند.

**اگر Redis از کار بیفتد چه؟** عمداً دو رفتار متفاوت:

- برای نقش‌های حساس (مدیر، مالی، پشتیبانی…): **بسته می‌شود** — خطای ۵۰۳
- برای زبان‌آموز و مدرس عادی: **باز می‌ماند**

منطق: اگر برای همه بسته می‌شد، یک اختلال کوچک Redis کل سایت را می‌خواباند. پنجرهٔ ۱۵ دقیقه‌ای
دقیقاً آنجا خطرناک است که دسترسی مدیریتی در کار باشد، و همان‌جا سخت‌گیری می‌شود.

## ۳. کنترل دسترسی

۱۳۹ مسیر API وجود دارد. هر کدام باید **یک تصمیم آگاهانه** دربارهٔ دسترسی داشته باشد:

| دسته | تعداد | یعنی |
| --- | --- | --- |
| عمومی | ۱۴ | عمداً بدون نیاز به ورود |
| نقش‌محور یا مجوزمحور | ۸۳ | فقط نقش‌های مشخص |
| «خودمحور» | ۴۲ | ورود لازم است ولی نقش خاصی نه — چون سرویس، داده را به خودِ کاربر محدود می‌کند |

### دربارهٔ آن ۴۲ مسیر

مثلاً `GET /users/me` نیازی به نقش ندارد؛ چون شناسهٔ کاربر از توکن گرفته می‌شود، نه از آدرس.
همهٔ ۴۲ مسیر یک‌به‌یک بررسی شدند تا مطمئن شویم واقعاً محدود به خودِ کاربرند. **هیچ نشتی پیدا
نشد.**

### تست زندهٔ IDOR

خطرناک‌ترین حملهٔ این دسته این است: کاربر A شناسهٔ سفارش کاربر B را حدس بزند.

**عملاً امتحان شد:** زبان‌آموز B با توکن معتبر خودش تلاش کرد برای رزرو زبان‌آموز A پرداخت بسازد.

```
نتیجه: 404 Not Found
```

نکتهٔ ظریف: پاسخ **۴۰۴** است، نه **۴۰۳**. اگر ۴۰۳ بود، یعنی «این وجود دارد ولی مال تو نیست» —
که خودش اطلاعات لو می‌دهد. ۴۰۴ یعنی «چنین چیزی برای تو وجود ندارد.»

### قفل کردن این وضعیت با تست

یک تست خودکار نوشته شد که همهٔ مسیرها را می‌خواند و هر مسیری که در هیچ‌کدام از سه دسته نباشد،
**بیلد را می‌شکند**.

> **این تست همان بار اول یک ایراد واقعی پیدا کرد:** مسیر `POST /auth/logout` عمومی بود، در هر
> فراخوانی به پایگاه داده می‌نوشت، و **هیچ سقفی نداشت**. یعنی یک راه رایگان برای فشار آوردن به
> پایگاه داده. برطرف شد.
>
> این مسیر قبلاً دو بار با چشم بازبینی شده بود و هر دو بار سالم به نظر رسیده بود.

## ۴. مواردی که بررسی شد و مشکلی نداشت

| ریسک | نتیجه |
| --- | --- |
| تزریق SQL | کوئری‌ها همه پارامتری‌اند. تنها SQL خام، `SELECT 1` برای بررسی سلامت است |
| XSS | فقط یک مورد `dangerouslySetInnerHTML` که از متغیر محیطی می‌آید نه از کاربر (بخش ۶) |
| Mass assignment | فرم پروفایل فقط نام، ایمیل، زبان، منطقهٔ زمانی و تاریخ تولد را می‌پذیرد. فیلدهای ناشناخته **رد** می‌شوند. `role` یا `balance` قابل ارسال نیست |
| ارتقای خودسرانه | `assignRole` و `grantPermission` صراحتاً رد می‌کنند که کاربر روی **خودش** عمل کند |
| SSRF | سرور هیچ آدرسی که کاربر داده باشد را واکشی نمی‌کند |
| ریدایرکت باز | `safeInternalPath()` جلوی آدرس‌های خارجی و `..` را می‌گیرد |
| رمز در گیت | کل تاریخچه بررسی شد: **هیچ فایل `.env` یا کلیدی هرگز کامیت نشده** |
| CORS | فقط یک دامنهٔ مشخص، نه `*` |
| آپلود فایل | نام فایل کاربر **هرگز** استفاده نمی‌شود؛ مسیر ذخیره `شناسهٔ‌کاربر/نوع/uuid.پسوند` است. سقف ۵۰ مگابایت. پسوند پاک‌سازی می‌شود |

## ۵. ایرادهای پیداشده

### SEC-205 — مسیرهای رزرو سقف نداشتند (متوسط — برطرف شد)

هر ۹ مسیر `/bookings` بدون محدودیت نرخ بودند. ساختن رزرو، یک قفل Redis می‌گیرد و تراکنش سنگین
اجرا می‌کند. یعنی کسی می‌توانست:

- **همهٔ ساعت‌های خالی یک مدرس را اشغال کند** (هر رزرو تا انقضای پرداخت، ساعت را نگه می‌دارد)
- با تولید تداخل مداوم، رزروکردن را برای بقیه مختل کند

برطرف شد: سقف ۳۰ درخواست در ۱۰ دقیقه روی ساختن، لغو و جابه‌جایی رزرو. مسیرهای خواندنی و
پذیرش/رد جابه‌جایی عمداً آزاد ماندند، چون ساعتی تخصیص نمی‌دهند.

### SEC-203 — الگوریتم امضای توکن قفل نشده بود (پایین — برطرف شد)

بررسی توکن بدون مشخص‌کردن الگوریتم مجاز انجام می‌شد.

**قابل سوءاستفاده نبود**، چون کلید متقارن است و کتابخانه هم `alg: none` را رد می‌کند. ولی اگر
روزی به کلید نامتقارن مهاجرت شود، حملهٔ «سردرگمی الگوریتم» بی‌صدا برمی‌گشت. حالا صراحتاً روی
`HS256` قفل شده.

### SEC-206 — خروج از حساب بدون سقف (پایین — برطرف شد)

توضیح در بخش ۳.

### SEC-201 — ۷ آسیب‌پذیری در کتابخانه‌ها (بالا — **باز**)

`npm audit`: ۷ مورد با شدت بالا، که **۵ تای آن‌ها در محیط تولید** حضور دارند:
`next`, `sharp`, `nanoid`, `@nestjs/swagger`, `js-yaml`.

ممیزی قبلی نوشته بود «۲ مورد، فقط در بخش وب». **این دیگر درست نیست** — مسیر
`@nestjs/swagger → js-yaml` در درخت وابستگی **API** است.

مهم‌ترینشان Next.js با ۸ هشدار، از جمله:
- SSRF در بازنویسی مسیر
- افشای بدون احراز هویت نقاط انتهایی داخلی
- سردرگمی حافظهٔ نهان

**بررسی شد:** پروژه از بازنویسی مسیر استفاده می‌کند (برای `/en`)، ولی مقصد بازنویسی از خودِ
مسیر درخواست ساخته می‌شود نه از دامنه‌ای که مهاجم بدهد — پس آن یک مورد قابل بهره‌برداری نیست.
بقیه رد نشده‌اند.

**چرا برطرف نشد؟** ارتقای نسخهٔ اصلی Next.js خودش یک پروژهٔ جداگانه با ریسک بازگشتی خودش است و
قواعد این ممیزی، ارتقای ناخواستهٔ وابستگی را ممنوع می‌کند. **این مهم‌ترین کار باقی‌مانده است.**

### SEC-202 — نوع فایل آپلودی بررسی محتوایی نمی‌شود (متوسط — باز)

نوع فایل بر اساس چیزی که **مرورگر ادعا می‌کند** بررسی می‌شود، نه محتوای واقعی. کسی می‌تواند
بگوید «این PNG است» و چیز دیگری بفرستد.

**اثر محدود است:** فایل‌ها روی MinIO/S3 ذخیره می‌شوند که دامنهٔ جداگانه‌ای است، پس XSS روی خودِ
سایت نیست. مسیر ذخیره هم هرگز از ورودی کاربر ساخته نمی‌شود.

**راه‌حل:** خواندن چند بایت اول فایل و مقایسه با امضای فرمت.

### SEC-204 — نماد اعتماد (اینماد) با `dangerouslySetInnerHTML` (پایین — پذیرفته‌شده)

اینماد یک قطعه HTML اختصاصی برای هر دامنه صادر می‌کند که باید عیناً درج شود. این مقدار از متغیر
محیطی می‌آید (در اختیار مدیر سیستم، نه کاربر).

**ریسک پذیرفته‌شده** — به شرط اینکه مدیر فقط همان قطعهٔ رسمی اینماد را قرار دهد.

## ۷. چه چیزی جلوی برگشتن این‌ها را می‌گیرد؟

- **تست ماتریس دسترسی**: هر مسیر جدید بدون تصمیم صریح، بیلد را می‌شکند
- **تست مرز ماژول‌ها**: جلوی وابستگی‌های پنهان بین بخش‌ها را می‌گیرد
- **تست بازگشتی برای هر ایراد**: هر اصلاح یک تست دارد که روی کد قبل از اصلاح شکست می‌خورد
- **`npm run lint` حالا واقعاً API را هم بررسی می‌کند** — تا پیش از این ممیزی، ۱۹۱ فایل API
  بی‌صدا رد می‌شدند و «سبز» فقط یعنی بخش وب سالم است
