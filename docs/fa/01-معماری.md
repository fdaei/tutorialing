# معماری

این سند توضیح می‌دهد سیستم از چه بخش‌هایی ساخته شده، چرا این‌طور تقسیم شده، و چه گزینه‌هایی
کنار گذاشته شده‌اند.

---

## ۱. نمای کلی

سه بستهٔ نرم‌افزاری در یک مخزن (monorepo) قرار دارند:

| بسته | مسیر | فناوری | نقش |
| --- | --- | --- | --- |
| `@lingospeak/web` | `apps/web` | Next.js 15 + React 19 | آنچه کاربر می‌بیند |
| `@lingospeak/api` | `apps/api` | NestJS 11 + Prisma + PostgreSQL | منطق کسب‌وکار و داده |
| `@lingospeak/contracts` | `packages/contracts` | Zod | تعریف‌های مشترک بین آن دو |

سرویس‌های جانبی: **PostgreSQL** (داده)، **Redis** (قفل، محدودیت نرخ، ابطال توکن)،
**MinIO** (فایل، سازگار با S3)، **BullMQ** (کارهای زمان‌بندی‌شده).

```
مرورگر
  │
  ├── Next.js (پورت ۳۰۰۰) ── middleware: زبان، CSP
  │        │
  │        └── fetch ──►  NestJS API (پورت ۴۰۰۱، پیشوند /api)
  │                          │
  │                          ├── PostgreSQL   ← تمام داده‌ها
  │                          ├── Redis        ← قفل، نرخ، ابطال
  │                          ├── MinIO/S3     ← فایل‌ها
  │                          └── زرین‌پال      ← پرداخت
```

### چرا مونوریپو؟

قراردادهای مشترک (شکل درخواست و پاسخ) باید در یک جا تعریف شوند تا وب و API از هم جدا نیفتند.
اگر دو مخزن جدا بودند، هر تغییر در قرارداد نیاز به انتشار نسخه و هماهنگی داشت.

**گزینهٔ ردشده:** کپی‌کردن تعریف‌ها در هر پروژه. قبلاً همین کار شده بود و به همین دلیل بستهٔ
`contracts` عملاً بلااستفاده مانده بود (توضیح در بخش ۵).

## ۲. ساختار API

هر بخش کسب‌وکار یک «ماژول» است زیر `apps/api/src/modules/`:

```
admin  auth  bookings  commerce  files  languages  learning
matching  queue  search  support  teachers  tests  users
```

درون هر ماژول، یک زنجیرهٔ ثابت رعایت می‌شود:

```
controllers/   فقط HTTP و نگهبان‌های دسترسی — بدون منطق و بدون کوئری
   ▼
services/      قوانین کسب‌وکار و تراکنش‌ها
   ▼
repositories/  کوئری‌های پیچیده یا تکراری
   ▼
dto/           اعتبارسنجی ورودی و شکل‌دهی خروجی
mappers/        تبدیل موجودیت پایگاه داده به پاسخ
```

**چرا؟** چون وقتی منطق در کنترلر باشد، تنها راه تستش بالا آوردن یک سرور HTTP است. با این
تفکیک، قوانین پول و رزرو را می‌شود بدون شبکه و بدون پایگاه داده تست کرد.

### گراف وابستگی ماژول‌ها

```
admin ─────► teachers
matching ──► bookings ──┬──► queue
                        └──► commerce
```

بقیهٔ ماژول‌ها برگ‌اند (به ماژول دیگری وابسته نیستند).

**هیچ وابستگی حلقوی وجود ندارد** — با ابزار `madge` روی ۱۹۲ فایل API و ۷۸ فایل وب بررسی شد.

### مرز ماژول‌ها؛ چیزی که در این ممیزی اصلاح شد

دو ماژول به **درون** ماژول دیگری دست می‌بردند:

- `queue` فایل `commerce/discounts/discount-reservation` را مستقیم import می‌کرد
- `bookings` فایل `commerce/payouts/earnings.service` را

مشکل این است که هر دو فایل، **قبلاً یک بار جابه‌جا شده بودند** (کامیت `3b04c00` پوشهٔ `commerce`
را به زیرپوشه‌ها تقسیم کرد). یعنی این وابستگی یک بار شکسته بود و با بازنویسی مسیرها وصله شده بود،
نه با ساختن یک مرز درست.

**راه‌حل:** یک فایل `commerce/index.ts` ساخته شد که فقط دو چیز را بیرون می‌دهد
(`EarningsService` و `releaseDiscount`). حالا `commerce` می‌تواند درونش را هرطور خواست بچیند
بدون اینکه دو ماژول دیگر بشکنند.

این مرز با **تست** نگهبانی می‌شود، نه با قانون lint. دلیلش در بخش ۶ آمده.

## ۳. ساختار وب

```
app/          مسیرها (App Router)
components/   کامپوننت‌ها — تخت، نه تودرتو بر اساس دامنه
lib/          api.ts (کلاینت)، i18n.ts، money.ts، panel-access.ts، format.ts
middleware.ts زبان + هدر امنیتی CSP
```

### زبان: چرا `/en` و نه `/fa`؟

فارسی روی مسیر خالی سرو می‌شود (`/teachers`) و انگلیسی زیر `/en` (`/en/teachers`).
`middleware.ts` مسیر انگلیسی را به همان مسیر اصلی بازنویسی می‌کند و یک هدر
`x-lingospeak-locale: en` اضافه می‌کند.

**چرا این‌طور؟** مخاطب اصلی محصول فارسی‌زبان است؛ آدرس تمیز و بدون پیشوند برای او طبیعی‌تر است
و برای موتور جست‌وجو هم بهتر.

**گزینهٔ ردشده:** پیشوند صریح `/fa` و `/en` برای هر دو. صریح‌تر است، ولی همهٔ آدرس‌های فعلی
عوض می‌شد و برای حفظ رتبهٔ جست‌وجو به ریدایرکت دائمی از تمام مسیرهای قبلی نیاز داشت. ارزشش را
نداشت.

### دسترسی به صفحات پنل

فایل `lib/panel-access.ts` یک فهرست **مجاز صریح** دارد: هر الگوی مسیر به یک شرط نقش یا مجوز
نگاشت می‌شود و **هر چیزی که در فهرست نباشد، ممنوع است**.

**چرا فهرست مجاز و نه فهرست ممنوع؟** چون اگر فردا صفحه‌ای اضافه شود و کسی یادش برود قانونش را
بنویسد، با فهرست ممنوع آن صفحه **باز** می‌ماند و با فهرست مجاز **بسته**. حالت پیش‌فرض باید امن
باشد.

## ۴. مدل داده

حدود ۱٬۲۰۰ خط تعریف در `apps/api/prisma/schema.prisma`. مهم‌ترین گروه‌ها:

| حوزه | جدول‌های کلیدی |
| --- | --- |
| هویت | `User`, `OtpChallenge`, `RefreshSession`, `Role`, `Permission` |
| مدرس | `Teacher`, `TeacherLanguage`, `TeacherPriceHistory` |
| زمان | `AvailabilityRule`, `AvailabilityOverride`, `Booking` |
| پول | `Payment`, `WalletEntry`, `Refund`, `Earning`, `PayoutBatch`, `PayoutItem`, `WithdrawalRequest`, `Reconciliation` |
| تخفیف | `Discount`, `DiscountRule` |
| بسته | `Package`, `Enrollment`, `CreditEntry` |
| آزمون | `TestDefinition`, `TestSection`, `Question`, `Attempt` |

### زبان به‌عنوان داده، نه کد

```
Language(code, nameFa, nameEn, nativeName, flag, direction, proficiencySystem)
TeacherLanguage(teacherId, languageId, levels[], specialties[])
```

اضافه‌کردن زبان جدید یعنی افزودن یک ردیف، نه تغییر کد. ستون `direction` هم دارد، پس زبان‌های
راست‌به‌چپ (مثل عربی) پشتیبانی می‌شوند.

### پول همیشه عدد صحیح

**هیچ ستون پولی از نوع اعشاری نیست.** ستون‌های اعشاری موجود، فقط نمرهٔ آزمون و امتیاز مدرس‌اند.
دلیلش در [سند مالی](02-مالی.md) به‌تفصیل آمده.

## ۵. بستهٔ `contracts` و درسی که داد

این بسته باید شکل‌های مشترک را نگه دارد. اما در ابتدا `main` و `types` آن مستقیم به فایل‌های
`.ts` اشاره می‌کردند. نتیجه: API که با CommonJS اجرا می‌شود نمی‌توانست آن را `require` کند و
برنامه هنگام اجرا خطا می‌داد. راه‌حل موقت تیم، **کپی‌کردن ثابت‌ها در هر برنامه** بود — یعنی
دقیقاً همان چیزی که بسته قرار بود جلویش را بگیرد.

حالا بسته هر دو قالب ESM و CommonJS را می‌سازد (دو بار اجرای `tsc` به‌علاوهٔ یک نشانگر
`{"type":"commonjs"}`).

**درس:** یک بستهٔ مشترک که نمی‌شود واقعاً استفاده‌اش کرد، بدتر از نبودنش است؛ چون توهم اشتراک
ایجاد می‌کند در حالی که کپی‌ها دارند از هم دور می‌شوند.

## ۶. تصمیم‌های معماری و بدیل‌هایشان

| تصمیم | چرا | بدیل ردشده |
| --- | --- | --- |
| PostgreSQL نه MongoDB | داده‌ها به‌شدت رابطه‌ای‌اند و پول به تراکنش واقعی نیاز دارد | MongoDB — تضمین تراکنشی ضعیف‌تر برای مسیر پول |
| Prisma نه SQL خام | تایپ امن و مهاجرت نسخه‌دار | SQL خام — سریع‌تر ولی مستعد تزریق و خطای تایپ |
| توکن بدون حالت (JWT) | نیازی به کوئری پایگاه داده در هر درخواست نیست | نشست در پایگاه داده — کندتر |
| نشانگر ابطال در Redis | JWT را نمی‌شود پس گرفت؛ این نشانگر آن را جبران می‌کند | عمر کوتاه‌تر توکن — فشار بیشتر روی سرور |
| مرز ماژول با **تست** نه lint | قانون `no-restricted-imports` در ESLint 9 الگو را اعمال نکرد و **بی‌صدا قبول شد** | قانون lint — خطرناک‌تر از نبودنش، چون سبزبودنش را «اثبات» می‌خوانند |
| `@nestjs/schedule` نه BullMQ برای تطبیق مالی | استفاده از BullMQ اولین وابستگی حلقوی مخزن را می‌ساخت | BullMQ — وابستگی موجود بود ولی گراف را خراب می‌کرد |

## ۷. نکته‌ای دربارهٔ Redis

Redis اینجا **چهار کار نامرتبط** را انجام می‌دهد: محدودیت نرخ، قفل ساعت رزرو، نشانگر ابطال
توکن، و قفل کار تطبیق مالی.

این یعنی اگر Redis از کار بیفتد، چهار چیز هم‌زمان تحت تأثیر قرار می‌گیرند — ولی **عمداً به شکل
متفاوتی**:

- محدودیت نرخ: **بسته می‌شود** (خطای ۵۰۳) تا مسیرهای حساس بی‌محافظ نمانند
- بررسی ابطال توکن: برای نقش‌های مدیریتی **بسته** و برای کاربر عادی **باز** می‌شود

منطقش این است: اگر برای همه بسته می‌شد، یک اختلال کوچک Redis کل سایت را می‌خواباند. پنجرهٔ
۱۵ دقیقه‌ای اعتبار توکن، جایی خطرناک است که کاربر دسترسی مدیریتی داشته باشد — و دقیقاً همان‌جا
سخت‌گیری می‌شود.

این بزرگ‌ترین سطح «سرنوشت مشترک» در سیستم است و در [کارهای باقی‌مانده](07-کارهای-باقی‌مانده.md)
ثبت شده.
