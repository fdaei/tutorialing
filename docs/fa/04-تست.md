# تست‌ها

## ۱. فلسفه: پوشش ریسک، نه درصد پوشش

هدف، رسیدن به عدد «۸۰٪ پوشش» نیست. عدد پوشش می‌تواند بالا باشد در حالی که هیچ‌کدام از مسیرهای
خطرناک واقعاً آزمایش نشده‌اند.

معیار ما این است: **اگر این خراب شود، چه کسی ضرر می‌کند؟** هر چه پاسخ بدتر، تست دقیق‌تر.

| وضعیت | تعداد |
| --- | --- |
| ابتدای ممیزی | ۱۹۳ |
| اکنون | **۲۱۸** |

---

## ۲. لایه‌های تست

### تست واحد — قوانین پول

فایل `money-invariants.spec.ts` قوانین ریاضی پول را روی شبکه‌ای از **۸ مبلغ × ۱۰ درصد** بررسی
می‌کند (شامل اعداد اول و مقادیری که بخش‌پذیر نیستند).

**نکتهٔ مهم دربارهٔ روش:** این تست‌ها فرمول‌ها را **دوباره می‌نویسند**، نه اینکه سرویس‌ها را صدا
بزنند.

چرا؟ چون تستی که کد اصلی را import کند و دوباره اجرا کند، فقط ثابت می‌کند «کد با خودش برابر
است» — نه اینکه قانون درست است. این تست‌ها قانونی را که ممیزی دستی بررسی کرده رمزگذاری می‌کنند.

مهم‌ترینشان: `کارمزد + سهم مدرس = مبلغ کل`، دقیقاً، برای هر ۸۰ ترکیب.

### تست ساختاری — مرز ماژول‌ها

`architecture.spec.ts` بررسی می‌کند هیچ بخشی به **درون** بخش دیگر دست نزند.

**اثبات شد که واقعاً کار می‌کند:** با برگرداندن موقتی یک import قدیمی، تست شکست و دقیقاً نوشت:

```
modules/queue/queue.service.ts -> ../commerce/discounts/discount-reservation
```

و با برگرداندن اصلاح، دوباره قبول شد. تستی که هرگز شکست نخورده، ارزشش معلوم نیست.

### تست ماتریس دسترسی

`authorization.spec.ts` همهٔ ۱۳۹ مسیر را می‌خواند و هر کدام را در یکی از سه دستهٔ زیر قرار
می‌دهد: عمومی، نقش‌محور، یا خودمحور (با فهرست صریح).

**مسیری که در هیچ‌کدام نباشد، بیلد را می‌شکند.** یعنی «یادم رفت نگهبان بگذارم» نمی‌تواند
بی‌صدا منتشر شود.

> این تست همان بار اول یک ایراد واقعی پیدا کرد (`POST /auth/logout` بدون سقف نرخ).

### تست بازگشتی برای هر ایراد

هر ایراد اصلاح‌شده یک تست دارد که **روی کد قبل از اصلاح شکست می‌خورد**.

این قانون قابل مذاکره نیست. تستی که قبل و بعد از اصلاح هر دو قبول شود، چیزی را اثبات نمی‌کند و
فقط توهم امنیت می‌سازد.

## ۳. اجرای تست‌ها

```bash
npm run test                       # همه
npm run test -w @lingospeak/api    # فقط API
npm run test -w @lingospeak/web    # فقط وب

npm run test -w @lingospeak/api -- money-invariants.spec.ts   # یک فایل
npm run test -w @lingospeak/api -- -t "commission"            # بر اساس نام

npm run verify   # دروازهٔ کامل: قالب‌بندی و اعتبارسنجی پایگاه داده + تایپ + lint + تست + بیلد
```

> ⚠️ تا پیش از این ممیزی، `npm run lint` بخش API را **بی‌صدا رد می‌کرد**. هر ادعای «همه‌چیز سبز
> است» در تاریخچهٔ این پروژه، فقط دربارهٔ بخش وب معتبر بوده. حالا هر دو بررسی می‌شوند.

## ۴. چه چیزی عمداً تست نشده

صداقت دربارهٔ حفره‌ها، از ادعای پوشش کامل ارزشمندتر است.

| مورد | دلیل |
| --- | --- |
| هم‌زمانی واقعی پایگاه داده | با پایگاه دادهٔ شبیه‌سازی‌شده قابل آزمایش نیست. به‌جایش، **سطح ایزولاسیون** تراکنش تست می‌شود |
| درگاه پرداخت واقعی | کلید فروشندهٔ واقعی در این محیط وجود ندارد |
| مسیر پرداخت **موفق** | نیاز به انسان روی صفحهٔ پرداخت آزمایشی دارد؛ فقط مسیر **شکست** زنده تأیید شد |
| تست‌های مرورگری (Playwright) | ۲ فایل وجود دارد ولی در این دور اجرا نشد |
| نمایش راست‌به‌چپ و فارسی | جز قالب‌بندی پول، ادعای دیگری نمی‌کنیم |
| اعتبارسنج کد ملی | چنین تابعی اصلاً در کد وجود ندارد که تست شود |

## ۵. اضافه‌کردن تست جدید

۱. **اگر باگ اصلاح می‌کنید:** اول تست را بنویسید و **روی کد خراب اجرا کنید**. اگر قبول شد،
   تستتان باگ را نمی‌سنجد.
۲. **اگر مسیر API اضافه می‌کنید:** یا `@Public()` بگذارید، یا نقش/مجوز، یا آن را به فهرست
   خودمحور اضافه کنید — و فقط وقتی که مطمئن شدید سرویس، داده را به خودِ کاربر محدود می‌کند.
۳. **اگر منطق پول را دست می‌زنید:** قانون را به‌صورت یک قاعده روی کل شبکهٔ اعداد اضافه کنید، نه
   یک مثال تکی.
۴. **اگر بین ماژول‌ها وابستگی می‌سازید:** تست ساختاری جلویتان را می‌گیرد؛ از فایل `index.ts`
   همان ماژول استفاده کنید.
